# Direct-to-Task Tutorial: creator-described direction (PROVISIONAL)

**Provenance:** The creator describes a YouTube tutorial channel with a preference for starting immediately, deleting irrelevant speech and using brisk editing while keeping actions understandable. Playlist: https://www.youtube.com/playlist?list=PLyyt5io0ZuEcc4A7Ipzcgl56ajGMMLrpJ . Access to individual videos and their frames/transcripts was throttled during this audit. **No claim that any specific video, timestamp, edit speed, opening or pause was observed.** The rules below are a transferable proposed direction, not an independent analysis of the playlist. Verify against native videos before claiming a measured channel fingerprint.

## Task-specific operating rules

1. **Start useful, not just fast.** Open with the answerable problem, the target setting, or the first demonstrable action. Omit unrelated origin stories and generic channel intros. Preserve a short prerequisite if otherwise viewers would be lost or unsafe.
2. **Edit speech by information value.** Candidate trims: repeated thesis, rambling, off-topic anecdote, avoidable greetings, abandoned sentences, duplicated explanations. Protect indispensable definitions, version caveats, safety warnings, caveats about irreversible actions, dependencies and context that change the outcome.
3. **Preserve action -> response -> outcome.** Every essential click, selection, dialog response and confirmation must be understandable on screen. Avoid hiding steps with jump cuts, zooms, motion graphics, or removing a wait that shows useful progress.
4. **Compress waiting, not thinking.** For a verified idle render/loading period, consider a speed ramp or hard cut with honest indication of skipped elapsed time. Keep enough time for labels, visually complex menus, error messages and changes to register. Do not follow fixed seconds-per-shot quotas.
5. **Use concise labels only when helpful.** Prefer short named steps, cursor focus, localized zoom and the setting value that matters. Preserve UI context. No mandatory narrative arc, fabricated stakes, subplot, cliffhanger or attention spikes.
6. **A replay is a viewer affordance, not a product objective.** Avoid designing confusion to force rewatches. Offer chapters, named steps, pauses, and easily located confirmations; let viewers rewind voluntarily. A spike in YouTube Analytics can indicate confusion as well as interest.
7. **Use native context before editing.** Dafin already has Whisper: reuse its transcript, correct misrecognitions, and align with real frame/audio samples. Speech recognition alone cannot tell whether an on-screen action is visible or sufficient. No source-clip mutation without project revision, undo, protected-range and consent gates.
8. **Be adaptive.** A fast one-click setting tutorial may need little exposition. A security change, multi-step install, or beginner workflow needs prerequisites and patient demonstrations. If the user explicitly requests a thorough/slow treatment, don't override it with this channel direction.

## Minimal evidence and review

- Need actual transcript/alignment and time-coded source visuals to label a sentence unnecessary or a waiting period idle. Metadata-only reviews return **candidate** trims, never approved edits.
- Prefer one short question only when audience expertise or required prerequisites materially change the edit. Do not require a style questionnaire for a clear tutorial.
- Review time to first useful action descriptively, not by universal seconds thresholds. Check step completeness, visible results, accessibility and user comprehension before measuring watch time.
- For native tests, compare complete first-view comprehension and task success as well as video length, editor effort and cost; don't treat looped replays as confirmed retention gains.
